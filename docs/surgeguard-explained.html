System walkthrough

SurgeGuard

A purchase-intake system built for traffic that arrives in bursts. It accepts money-moving requests without ever making the caller wait on a payment provider, and it is designed so that a surge produces a queue rather than an outage, a double charge, or lost work.

01

What the system actually does

A client posts a purchase. SurgeGuard writes it down, answers 202 Accepted immediately, and charges it later on its own schedule. Everything else in the system exists to make those three moves safe.

Concretely, there are four moving parts. An HTTP API takes purchase requests and refuses to do any expensive work inline. A background worker picks that work up and runs it against a simulated payment provider at a strictly bounded concurrency. A reconciler sweeps up anything a crashed worker abandoned. An operations dashboard shows the whole thing moving in real time, so the behaviour under load is something you watch rather than something you take on trust.

The payment provider is simulated on purpose — a configurable sleep plus a configurable failure rate. The interesting engineering here is not the integration with a card network; it is everything around it: what happens when 500 requests land at once, when the client retries a request whose response it never saw, and when a worker is killed halfway through a charge.

02

The problem it solves

Start with the naive version: the endpoint calls the payment provider inline and returns 201 Created when the charge succeeds. It is the obvious design, and under a surge it fails four different ways at once.

Failure 1

Unbounded downstream load

500 concurrent HTTP requests become 500 concurrent calls to the payment provider. It rate-limits you, or it falls over, and now the outage is shared.

Failure 2

Lost work

The request thread dies mid-flight — deploy, OOM, timeout. The customer saw a spinner or a success; the purchase simply evaporated. Nothing on disk knows it ever existed.

Failure 3

Duplicate charges

The client never received the response, so it retries. It gets charged twice. This is the failure that costs real money and real trust.

Failure 4

The enqueue gap

Bolting on a job queue introduces a new failure: the window between "row committed" and "job enqueued". Crash in that window and the database says accepted while nothing will ever process it.

Retries alone do not fix any of these — retries make failure 3 worse. A job queue alone fixes failure 1 and creates failure 4. The design below closes all four, and it does it with database primitives rather than application bookkeeping, which is what makes the guarantees survive running many processes on many machines.

03

The one design rule

Accepting work and doing work are separate concerns with separate capacity.

Intake is cheap, non-blocking, and scales with traffic. Processing is expensive, strictly bounded, and scales with backlog. Between them sits a transactional outbox, which is the piece that makes a surge produce a queue instead of an outage.

Every other decision in the repository is downstream of that sentence. Intake latency is one database write, whatever is happening behind it. Downstream concurrency is a number in a config file — 5 threads per worker process — not a function of how many people are hitting the site. The backlog is a queryable table, so "are we keeping up?" is a SQL question with a real answer rather than a guess.

04

Life of a request, step by step

Follow one purchase from the client's POST to a processed row. This is the sequence to walk someone through if you only have time for one thing.

  1. The client sends an idempotency key, or gets rejected

    The controller requires an Idempotency-Key header and answers 400 without it. This is deliberately not optional: the entire retry-safety story depends on the client naming its request, and a system that lets callers skip that has no way to tell a retry from a second purchase.

    api/app/controllers/api/v1/purchase_requests_controller.rb

  2. A per-IP token bucket decides whether to even look at the body

    A Redis INCR-plus-EXPIRE Lua script counts requests per IP in a 10-second window, defaulting to 200. Over the limit is 429. If Redis is unreachable, the limiter fails open and lets the request through — losing rate limiting is strictly better than losing intake.

    api/services/request_rate_limiter.rb

  3. One transaction writes the purchase and its outbox event

    This is the load-bearing step. The purchase_requests row (status queued) and an outbox_events row (purchase.created) are committed together, so there is no instant in time where one exists and the other does not. Crash before commit and neither exists; crash after commit and the work is durably recorded and durably scheduled. That closes the enqueue gap.

    PurchaseRequest.transaction do
  purchase = PurchaseRequest.create!(
    idempotency_key: idempotency_key,
    status: :queued, …)

  OutboxEvent.create!(
    event_type: "purchase.created",
    aggregate_id: purchase.id, …)
end

  4. Duplicates are adjudicated by the database, not by a check

    A unique index on idempotency_key raises ActiveRecord::RecordNotUnique, which the controller rescues. If the payload matches the stored row, it returns the original purchase with 200 OK — retry forever, safely. If the payload differs, that is a client bug and it gets 409 Conflict.

    There is deliberately no Rails uniqueness validation on the model. That would be a check-then-insert race: two simultaneous requests both read "no such key", both pass validation, and one blows up anyway — with the graceful duplicate handling never reached. The database is the only thing that can adjudicate simultaneity, so it does.

    api/app/models/purchase_request.rb — the comment above the validations says exactly this

  5. 202 Accepted returns; no provider was contacted

    Intake latency is one insert pair, regardless of how backed up processing is. That decoupling is the whole point: under a surge the response time of the endpoint does not move.

  6. A dispatcher claims outbox events once a second

    OutboxDispatchJob selects up to 100 pending events with FOR UPDATE SKIP LOCKED and turns each into a ProcessPurchaseJob, then stamps published_at. Because the claim is a row lock that competing dispatchers skip rather than block on, any number of dispatcher processes can run concurrently and no two will ever claim the same event. That is what makes the worker tier horizontally scalable.

    api/jobs/outbox_dispatch_job.rb · schedule in api/config/recurring.yml

  7. The bounded worker pool does the expensive part

    ProcessPurchaseJob runs on the transactions queue with 5 threads per worker process. It moves the purchase queued → processing → processed, stamping processing_started_at, attempt_count and processed_at along the way. Two guards make redelivery harmless: limits_concurrency(to: 1, key: purchase_request_id) means the same purchase is never worked twice at the same moment, and an early return if purchase.processed? makes a duplicate delivery a no-op.

    Total downstream concurrency is therefore 5 × worker_count — a number you choose, not a number the traffic chooses. Everything else waits in queued.

    api/jobs/process_purchase_job.rb · pools in api/config/queue.yml

  8. Failures are recorded, reverted, and retried with backoff

    On exception the job writes last_error, puts the purchase back to queued, and re-raises so Solid Queue's retry_on … :polynomially_longer, attempts: 5 takes over. The row always tells you what went wrong and how many times it has been tried.

  9. The reconciler redrives whatever was abandoned

    If a worker is killed while a purchase is processing, nothing would ever touch that row again — the job is gone and the status is not queued. Every 30 seconds ReconcileStuckPurchasesJob finds purchases that have been processing for more than 2 minutes, returns them to queued, and writes a fresh outbox event to drive them again. This is the layer that covers deploys, scale-ins, spot interruptions and OOM kills.

    api/jobs/reconcile_stuck_purchases_job.rb

  10. Operators watch it through /metrics

    GET /api/v1/metrics returns purchase counts by status, pending outbox depth, and the age of the oldest unpublished event. Age is the honest health signal — a small stalled backlog is far worse than a large one that is draining, and a count alone cannot tell those apart.

    api/app/controllers/api/v1/metrics_controller.rb
05

The data model

Two tables in the primary database, plus Solid Queue's own tables in a separate database so queue churn does not compete with transactional data for the same IO.

purchase_requests

ColumnTypeWhy it is there
idempotency_keystringUnique index. The entire retry-safety guarantee lives on this one constraint.
customer_refstringWho the purchase belongs to; compared on duplicate keys to detect a 409.
amount_centsintegerInteger cents, never floats. Check constraint amount_cents > 0 at the database level.
statusenumqueued · processing · processed · failed, indexed because every metric groups on it.
attempt_countintegerHow many times processing has been tried — visible in the dashboard.
processing_started_atdatetimeThe clock the reconciler reads to decide a row is stuck.
processed_atdatetimeCompletion timestamp.
last_errortextThe failure message, kept on the row so debugging does not require log archaeology.

outbox_events

ColumnTypeWhy it is there
event_typestringCurrently only purchase.created; the dispatcher switches on it.
aggregate_type / aggregate_idstring / bigintWhat the event is about. Indexed together.
payloadjsonbEvent body. The reconciler marks its redrives with recovery: true.
published_atdatetimeNull means pending. Indexed — this is the column the dispatcher scans every second.
attempt_count / last_errorinteger / textPublish attempts and the last publish failure.
06

Guarantees, and what actually enforces them

The reason to read this table rather than the prose: each property is held up by a database primitive, not by application bookkeeping. That is what makes it survive many processes, many machines, and a deploy in the middle.

GuaranteeMechanism
One idempotency key creates exactly one purchase, however many concurrent requests carry it Unique index + rescue RecordNotUnique returning the existing record. Not a model validation, which would be a check-then-insert race.
Reusing a key with a different payload is rejected, not silently misresolved The duplicate handler compares customer_ref and amount_cents and returns 409 on mismatch.
Accepted work is never lost between the HTTP response and the job Purchase row and outbox event share one transaction. No window exists where one is true and the other is not.
Concurrent dispatchers never double-claim an event SELECT … FOR UPDATE SKIP LOCKED.
A purchase is never processed twice concurrently, and a redelivery never re-runs a finished one limits_concurrency(to: 1, key: purchase_request_id) plus an early return if purchase.processed?.
A surge produces a bounded backlog, not unbounded downstream load Downstream concurrency is exactly transactions pool threads × worker count. Intake is unaffected.
Work abandoned mid-flight is recovered automatically ReconcileStuckPurchasesJob on a 30-second recurring schedule.
One client cannot monopolise intake Redis token bucket per IP, failing open when Redis is down.
Listing purchases cannot be made to return an unbounded result set per_page clamped server-side to 200 regardless of what the caller asks for.
07

How it was built, in order

This is the build sequence, and the order matters — each step exists because the previous one left something unsafe. If you are explaining the project to someone, this section is the narrative.

  1. Scaffold the API in API-only mode

    Rails 8.1, Ruby 3.4, PostgreSQL, --api. Rails 8's default stack is already the right one here: Solid Queue for jobs, Solid Cache, Thruster and Puma in the production image, Kamal for deploys, Brakeman and RuboCop wired into bin/ci. Nothing was replaced.

    api/ · Gemfile adds only redis and rack-cors on top of the default stack

  2. Write the two migrations before any application code

    The constraints are the design, so they came first: the unique index on idempotency_key, the amount_cents > 0 check constraint, the status index, and the published_at index the dispatcher scans. Application code was written afterwards to fit them.

    api/db/migrate/20260820181858_create_purchase_requests.rb · …182455_create_outbox_events.rb

  3. Model the aggregate — and deliberately leave uniqueness out

    PurchaseRequest gets a status enum, presence and numericality validations, and an amount_dollars helper. It does not get validates :idempotency_key, uniqueness: true, and there is a comment on the model explaining why, because the omission looks like an oversight to every reviewer until it is explained.

  4. Build intake around the transaction, then the rescue

    The controller's create is one transaction writing both rows, a 202, and three rescues: RecordNotUnique for idempotent replay, RecordInvalid for 422, and a missing header for 400. The duplicate handler is where 200 versus 409 is decided.

  5. Add the outbox dispatcher with SKIP LOCKED

    Batches of 100, ordered by id, claimed inside a transaction. A publish failure is caught per event: attempt_count and last_error are recorded and the event is left pending, so one bad event cannot abort the batch around it.

  6. Add the processing job with its two idempotency guards

    Per-purchase concurrency limit, the processed-already short circuit, polynomial backoff over 5 attempts, and the simulated provider behind two environment variables — PAYMENT_LATENCY_MS and PAYMENT_FAILURE_RATE — so flaky-downstream behaviour can be demonstrated on demand rather than described.

  7. Add the reconciler for the crash case

    Two minutes in processing is treated as abandoned. The row goes back to queued with an explanatory last_error, and a new outbox event redrives it — reusing the existing dispatch path rather than enqueuing directly, so recovery flows through exactly the same machinery as first delivery.

  8. Turn the concurrency bound into configuration

    queue.yml declares two pools: transactions with 5 threads and fast 0.1s polling, and maintenance with 2. recurring.yml schedules outbox dispatch every second and reconciliation every 30. Solid Queue gets its own database via QUEUE_DATABASE_URL.

    Splitting the pools matters: maintenance work must not be starved by a transactions backlog, or the dispatcher stops feeding the very queue that is backed up.

  9. Add the rate limiter as a Redis Lua script

    INCR plus a conditional EXPIRE in one atomic script, so the window cannot leak on a race. The rescue around Redis::BaseError returning true is the deliberate fail-open decision.

  10. Expose the operator surface

    /api/v1/metrics for the gauges, a paginated index with a server-side hard cap, and Rails' built-in /up as the container and load-balancer probe. CORS origins come from an environment variable so the same build works locally, in compose, and behind CloudFront.

  11. Promote jobs and services out of app/

    api/jobs/ and api/services/ sit at the top level and are added to the autoload paths in config/application.rb. These three jobs are the system; burying them under app/ alongside generated boilerplate would have hidden the substance of the design.

  12. Write the tests as named scenarios

    Nine behaviours were specified up front and the tests are labelled with them — the idempotency storm, conflicting key reuse, retry safety, durable failure recording, stuck-record reconciliation, concurrent dispatch, bounded backlog, bounded pagination, and the end-to-end lifecycle. The test names read as claims about the system, not as descriptions of methods.

  13. Build the dashboard as a demonstration device

    React 19 + Vite + TypeScript, polling /metrics and the purchase list once a second. The idempotency key is an editable field — that is the point of the UI, not a debug affordance. Resubmit the same key and watch the original record come back; change the amount and watch a 409. The table pages with "Load more" so it stays bounded no matter how many purchases exist.

    dashboard/src/App.tsx · api.ts · types.ts

  14. Write load scripts, because concurrency claims need evidence

    Three TypeScript scripts that drive a running stack: load-test.ts for sustained throughput, idempotency-storm.ts which fires N simultaneous requests under one key and then verifies exactly one purchase exists, and backlog-check.ts which bursts a batch and polls /metrics to show processing pinned at the pool size while queued absorbs the surge.

  15. Containerise the whole stack, with the split that production has

    docker-compose.yml brings up Postgres, Valkey, the API, a worker, and the dashboard. api and worker run the same image with different commands, mirroring the production split of one service for Puma and a separately scaled service for the queue.

  16. Consolidate into one monorepo with one CI pipeline

    The API originally carried its own nested git repository; it was collapsed so a single .github/workflows/ci.yml covers all three subprojects. Five jobs: Ruby security scan, RuboCop, Rails tests against real Postgres and Valkey service containers, the dashboard (format, oxlint, ESLint, typecheck, build, Vitest), and the load scripts (format, typecheck).

  17. Write the AWS mapping instead of provisioning AWS

    docs/aws-architecture.md maps every compose service onto CloudFront/S3, ALB, ECS Fargate, RDS, ElastiCache and CloudWatch; names which metric scales which service; and is explicit that the move needs no application code changes, because the guarantees are Postgres primitives rather than in-process state. It also names what does need adapting — chiefly that recurring jobs must run in exactly one place.

08

Running it

Everything at once

docker compose up --build
# dashboard → http://localhost:5173   api → http://localhost:3000

Natively — needs Ruby 3.4, Node 22, PostgreSQL, Redis

# terminal 1 — API
cd api && bundle install && bin/rails db:prepare && bin/rails server

# terminal 2 — worker. Nothing is processed without this.
cd api && bin/jobs start

# terminal 3 — dashboard
cd dashboard && npm install && npm run dev

The worker is not optional. Without bin/jobs start, purchases are accepted and durably stored but sit in queued forever — both dispatch and processing run through Solid Queue. This is the first thing to check when a demo looks broken.

Proving the claims

cd loadtest
npx tsx load-test.ts 500 50          # 500 requests, 50 concurrent
npx tsx idempotency-storm.ts 100     # 100 requests, one shared key
npx tsx backlog-check.ts 300 10      # 300-request burst, expect processing ≤ 10

backlog-check.ts reports rate-limited requests separately — bursting past RATE_LIMIT_MAX trips the limiter, which is correct behaviour rather than a failed run. Raise the limit to burst harder.

10

What you get from building it this way

Latency

Intake latency is flat under load

The endpoint does two inserts and returns. A 10× traffic spike changes the size of the queue, not the response time.

Money

Retries are free

A client can retry the same key indefinitely and get the same purchase back. That removes the single most expensive class of bug in payments.

Durability

Nothing accepted is ever silently dropped

Work is recorded and scheduled in the same commit, and anything abandoned mid-flight is swept back into the queue within 30 seconds.

Blast radius

The provider is protected from your traffic

Downstream concurrency is a number you set. A surge cannot turn into a thundering herd against a third party.

Scaling

Two tiers scale on two different signals

Web scales on request rate; workers scale on backlog depth and age. Both signals are already exposed by /metrics.

Operations

The backlog is queryable

It is a Postgres table. "What is stuck, since when, with what error" is a SQL question, not a log-scraping exercise.

Portability

Moving to AWS changes no application code

Every guarantee is a Postgres primitive, so there is no in-process state to make sticky and no coordinator to add — only environment variables and task definitions.

Simplicity

One fewer service to operate

Solid Queue means no separate broker. Postgres was already a hard dependency; the queue rides along in its own database.

11

What it does not solve

Read this section before presenting the system to anyone. Every item here is a real gap in the code as it stands, not a hypothetical. Knowing them is the difference between demonstrating a design and overselling one.

Exactly-once charging is not achieved — and cannot be, here

Correctness

The guard against double work is return if purchase.processed?, which reads the status we wrote. If a worker dies after the provider accepted the charge but before the row is updated, the purchase is redriven and charged again. Delivery is at-least-once; true idempotency has to be enforced by the provider, by sending it an idempotency key of its own and trusting its dedupe.

Not visible in a demo, because the provider is simulated and has no ledger.

Retry exhaustion has no terminal state

Correctness

After 5 failed attempts the job is discarded. The purchase is left in queued with a last_error, and nothing ever picks it up again — the reconciler only redrives rows stuck in processing. The failed status exists in the enum and is reported by /metrics, but no code path ever sets it, so that gauge is permanently zero.

Fix: a dead-letter transition on retry exhaustion, plus an alert on it.

A poison outbox event retries forever

Correctness

An event the dispatcher cannot publish — an unknown event_type, say — has its error recorded but published_at left null, so it is reclaimed on the next tick. Every second. Indefinitely. There is no attempt ceiling and no quarantine, so one bad row becomes a permanent log fire and permanently inflates the pending-backlog gauge that drives autoscaling.

The stuck-work threshold is a fixed two minutes

Correctness

Any purchase legitimately in flight for longer than two minutes will be redriven as if abandoned. The concurrency limit and the processed-check make that mostly harmless, but it is a hardcoded assumption about provider latency rather than a derived one.

There is no authentication or authorisation at all

Security

Anyone who can reach the API can create purchases, list every purchase in the system, and read the metrics. No API keys, no tenancy, no scoping of the list endpoint to a customer. The listing endpoint alone is a data-exposure problem the moment it is not on localhost.

Rate limiting is weaker than it looks

Security

It is a fixed 10-second window, so a caller can send 2× the limit across a window boundary. It keys on request.remote_ip, which behind a load balancer is only as trustworthy as the proxy configuration. It is per-IP, so a distributed client is unaffected and a shared NAT is punished. And it fails open — the right call for availability, but it means the limiter is absent exactly when Redis is having a bad day.

No client can look up its own purchase

Product

The routes are index and create only. There is no GET /purchase_requests/:id and no lookup by idempotency key, so a client that got a 202 has no supported way to ask "what happened to it?" other than paging the global list. There are also no callbacks or webhooks back to the caller, no cancellation, and no refunds.

The read path will not scale with the write path

Performance

/metrics runs five COUNT(*) queries per call and the dashboard polls it once a second per open tab. The listing uses OFFSET pagination, which degrades on deep pages, and the dashboard re-fetches every loaded page on each poll. Fine for a demo with thousands of rows; not fine at millions.

Observability stops at one JSON endpoint

Operations

There is no metrics export, no tracing, no alerting, and no dashboards beyond the React page. The AWS document describes shipping these gauges to CloudWatch and the alarms to hang off them, but none of that is implemented — and neither is any autoscaling. The scaling story is a written plan, not running infrastructure.

Nothing here handles money or PII properly yet

Compliance

No card data, no encryption at rest beyond whatever the database provides, no audit trail of who changed what, no PCI scope analysis, no ledger or double-entry accounting. amount_cents is an integer with no currency field, so the system is implicitly single-currency.

The deployment story is single-region and untested

Operations

The AWS topology is a written mapping, deliberately not Terraform, so no infrastructure has ever been provisioned from it. There is no disaster recovery plan, no multi-region story, and no database migration or backup runbook. The compose stack itself could not be verified in the environment where this was built, because Docker was unavailable there.

Load tests are not part of CI

Testing

The loadtest CI job only formats and typechecks; the scripts need a live stack, so they are run by hand. That means the concurrency properties are demonstrated on demand rather than continuously defended against regression. There is also no browser-level end-to-end test — the dashboard is covered by Vitest with a mocked API, not by a real browser driving a real backend.

12

If this went live, in priority order

The first five changes

  1. Authentication and per-tenant scoping, plus a GET for a single purchase. Without these the API is not deployable outside a private network.
  2. A terminal failure state. Transition to failed on retry exhaustion, alert on it, and give the outbox a publish-attempt ceiling with quarantine so a poison event stops burning a dispatcher tick every second.
  3. Provider-side idempotency. Send the payment provider its own idempotency key so a crash between charge and status update cannot double-charge.
  4. Metrics to CloudWatch and autoscaling policies — backlog age on the worker service, request rate on the web service — and a dedicated single-task scheduler service so recurring jobs run in exactly one place.
  5. Make the read path cheap: cached or incrementally maintained counters instead of COUNT(*) per poll, and keyset pagination instead of OFFSET.
13

The two-minute version

If someone gives you two minutes, say this. Under a holiday surge the dangerous failures are not slowness — they are taking a customer's money twice and returning 202 for work that then evaporates. SurgeGuard separates accepting work from doing work: intake writes the purchase and an outbox event in a single transaction and returns immediately, so accepted work can never be lost in the gap between the response and the job.

Duplicates are settled by a unique index rather than an application check, because only the database can adjudicate two simultaneous requests. A dispatcher claims outbox events with FOR UPDATE SKIP LOCKED, so any number of workers can run without double-claiming. Processing runs in a pool of fixed size, so a surge produces a queue rather than a thundering herd against the payment provider. A reconciler redrives anything a dead worker abandoned.

Then be honest about the edges: delivery is at-least-once, so true exactly-once charging needs the provider's own idempotency; retry exhaustion currently has no terminal state; and there is no authentication yet. Those are the three things to fix first.
